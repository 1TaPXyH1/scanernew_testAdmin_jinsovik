## 1. Резюме аудиту

**Загальний стан проєкту:** Проєкт перебуває на ранній стадії розробки. Основна функціональність сканування штрихкодів реалізована та працює, але містить критичні проблеми безпеки, архітектурні недоліки та відсутність тестування.

**Призначення продукту:** Мобільний застосунок для сканування штрихкодів товарів (EAN-13 з префіксом 210700) з можливістю перегляду цін, залишків у магазинах мережі, а також проведення переобліку товарів з генерацією PDF-звітів. Цільові користувачі — працівники торговельної мережі.

**Готовність до релізу:** НЕ ГОТОВИЙ до виробничого використання. Потребує значної роботи перед релізом.

**Найсильніші сторони:**
- Зручний UI з темною темою, анімованими переходами та візуальним зворотним зв'язком
- Статичний аналіз проходить без помилок (`flutter analyze` — 0 issues)
- Добре продуманий UX сканування (центрування штрихкоду, вібровідгук, ручне введення)
- PDF-генерація звітів з групуванням за статтю товару та підрахунком підсумків
- Використання актуальних версій Flutter (3.44) та Dart (3.12)

**Найслабші сторони:**
- Відсутність тестування (0 тестів)
- Критичні проблеми безпеки (відсутність автентифікації, дебажні ключі підпису релізу, відкрите сховище даних)
- Бізнес-логіка в UI-шарі замість сервісів
- Дублювання коду (~129 рядків)
- Відсутність інкапсуляції конфігурації (API URL жорстко закодовано)

**Кількість знахідок за серйозністю:**
- Critical: 5
- High: 12
- Medium: 10
- Low: 9
- Improvement: 4

**Основні виробничі ризики:**
1. Витік API endpoint та всієї товарної бази через відсутність автентифікації
2. Можливість підміни релізного APK через дебажний підпис
3. Втрата даних сесій переобліку через незахищене JSON-сховище
4. Падіння застосунку через `null`-пойнтер при використанні `_sessionManager!`
5. Збій при фоновому записі даних у `dispose()`

**Підсумкова рекомендація:** Провести Етап 0 (негайні виправлення безпеки) та Етап 1 (підготовка до релізу) перед будь-яким публічним розгортанням. Без цього продукт несе неприйнятні ризики для бізнесу та користувачів.

## 4. Критичні та високопріоритетні проблеми

### CRIT-01: Відсутність автентифікації API

| Поле | Значення |
|---|---|
| **Серйозність** | Critical |
| **Пріоритет** | P0 |
| **Впевненість** | Висока |
| **Категорія** | Безпека |
| **Файли** | `lib/services/api_config.dart:2`, `lib/screens/result.dart:47-49`, `lib/recount/recount_new_scan_screen.dart:181-184` |

**Опис:** HTTP GET запити до API виконуються без жодних заголовків авторизації, токенів чи API-ключів.

**Доказ:** 
```dart
final response = await http.get(Uri.parse(
  ApiConfig.productUrl(widget.barcode),
)).timeout(const Duration(seconds: 10));
```

**Сценарій атаки:** Будь-хто, хто витягне URL з APK (за допомогою `apktool` або `dex2jar`), може напряму викликати API — запитувати будь-які штрихкоди, перераховувати товари та, потенційно, виявити інші REST endpoint через path traversal.

**Вплив:** Повний витік товарної бази з цінами та залишками.

**Рекомендація:** Додати API-ключ або Bearer token до всіх запитів. Валідувати на стороні сервера.

**Складність:** Середня (потребує змін на клієнті та сервері).

**Верифікація:** HTTP-запит без токена має повертати 401.

### CRIT-05: `_saveSession()` без `await` у `dispose()`

| Поле | Значення |
|---|---|
| **Серйозність** | Critical |
| **Пріоритет** | P0 |
| **Впевненість** | Висока |
| **Категорія** | Data loss |
| **Файли** | `lib/recount/recount_new_scan_screen.dart:93` |

**Опис:** `dispose()` — синхронний метод, а `_saveSession()` повертає `Future<void>`. Результат не очікується (fire-and-forget). Те саме на рядку 111 (`didChangeAppLifecycleState`).

**Доказ:**
```dart
void dispose() {
  _saveSession(); // Future<void> — не очікується
}
```

**Вплив:** Дані сесії можуть бути втрачені при закритті екрану або переході у фон.

**Рекомендація:** Використовувати `WidgetsBinding.instance.addPostFrameCallback` з `await` або переробити архітектуру збереження.

**Складність:** Середня.

## 7. UX-аудит

### Знайдені проблеми

1. **Непослідовне повідомлення про помилки** (MED-09): Помилки сервера показують код статусу користувачу ("Помилка сервера: 500"), що не є зрозумілим для звичайного користувача.

2. **Неочікувана навігація назад** (MED-09): Після сканування користувач потрапляє на `ResultsScreen` через `pushReplacement`. Кнопка "Сканувати ще" робить `pushAndRemoveUntil`, що руйнує стек навігації — кнопка "Назад" не повертає до сканера, а виходить із застосунку.

3. **Відсутність онбордингу** (LOW): Новий користувач не отримує пояснення, що означають префікси штрихкодів або як користуватись переобліком.

4. **Зникаюча помилка** (Medium): Повідомлення про помилки зникають через 1.5 секунди. Користувач може не встигнути прочитати.

5. **Порожня кнопка налаштувань** (LOW-05): Іконка шестерні на головному екрані нічого не робить, але виглядає як активний елемент керування.

6. **Неочевидний вибір магазину** (Low): Вибір магазину реалізовано через `showModalBottomSheet`, але позначка "Вся мережа" як магазин може вводити в оману — це фільтр, а не магазин.

7. **Немає підтвердження перед скануванням** (Improvement): Користувач натискає на екран і одразу починається сканування. Немає можливості перервати до виявлення штрихкоду.

8. **Список товарів без сортування** (Improvement): У списку товарів переобліку немає сортування за назвою, ціною або різницею.

## 10. Аудит frontend

### Управління станом
- **Provider** використовується, але неконсистентно: `Provider.of<X>(context)` замість `context.watch<X>()` / `context.read<X>()`
- `SessionStorage` є одночасно моделлю, сховищем і ChangeNotifier — порушення SRP
- `RecountSessionManager` залежить напряму від конкретного `SessionStorage`, а не від інтерфейсу

### Компоненти
- **Дублювання** `_ScanOverlayClipper` та `_ScanCornersPainter` у двох файлах
- **Невикористаний параметр**: `RecountProductListScreen` отримує `products` через конструктор, але читає з Provider
- **Витоки пам'яті**: `TextEditingController` без `dispose()` у діалогах

### Асинхронність
- **Fire-and-forget**: `_saveSession()` у `dispose()` без `await`
- **Відсутні перевірки `mounted`**: У `result.dart` після `await` перед `setState()`
- **Force-unwrap** `_sessionManager!` у 8 місцях

### API/Мережа
- HTTP-клієнт не інкапсульовано — прямі виклики `http.get()` у віджетах
- Відсутні обробники `TimeoutException` у деяких місцях
- Немає повторних спроб при збої мережі
- `NetworkService()` створюється кожного разу, а не через DI

## 11. Аудит backend та API

Оскільки backend не входить до складу цього репозиторію, аудит обмежується клієнтською частиною.

### Клієнтські виклики API

1. **Формат запиту**: `GET {baseUrl}/REST/hs/prices/product_new/{barcode}/`
2. **Очікувана відповідь**: `{"success": true, "response": [{good, price}, [{name, remaining, size, telephone}]]}`
3. **Відсутня автентифікація** (CRIT-01)
4. **Статус-коди** відображаються користувачу (MED-02)
5. **Немає обробки різних форматів помилок** — тільки statusCode 200 вважається успіхом
6. **Немає версіонування API** в URL

### Поведінка при помилках

| Сценарій | Поведінка | Оцінка |
|---|---|---|
| 200 OK, `success: false` | Показується "Товар не знайдено" | Адекватно |
| HTTP 4xx/5xx | Показується код помилки | Забагато інформації |
| Timeout (10s) | "Сервер не відповідає" | Адекватно |
| Network error | "Помилка з'єднання" | Адекватно, але без деталей |
| Пуста відповідь | Catch → "Помилка з'єднання" | Може маскувати помилку сервера |

## 12. Аудит бази даних

Застосунок не використовує реляційну базу даних. Сховищем є JSON-файл.

### Проблеми JSON-сховища (`session_storage.dart`)

1. **Відсутність транзакційності**: Якщо запис перерветься — файл пошкоджено (HIGH-11)
2. **Конкуренція**: Декілька одночасних записів можуть перезаписати один одного
3. **Відсутність індексів**: Пошук сесії виконується лінійним пошуком (`firstWhere`)
4. **Неефективний запис**: Кожна операція записує весь файл, навіть при зміні одного поля
5. **Типобезпека**: `.cast<Map<String, dynamic>>()` може викинути помилку під час виконання
6. **Даних багато**: При багатьох сесіях файл може стати великим — немає пагінації або архівування

### Рекомендації
- Замінити на SQLite (через `sqflite` або `drift`) для транзакційності та індексів
- Або використовувати `flutter_secure_storage` для чутливих даних
- Додати автоматичне резервне копіювання

## 14. Аудит продуктивності

### Виміряні проблеми

1. **Неефективний запис JSON** (HIGH-11): Кожна операція збереження записує цілий файл заново. При десятках товарів це може створювати помітну затримку на повільних пристроях.

2. **Немає кешування API відповідей** (Low): Кожне сканування виконує новий HTTP-запит, навіть якщо той самий штрихкод сканувався хвилину тому.

3. **NetworkService створюється кожен виклик** (LOW-03): Створення об'єкта `Connectivity()` при кожному скануванні — зайві витрати.

4. **Відсутність lazy loading** (Low): Список усіх товарів у переобліку завантажується повністю.

### Потенційні ризики

1. **N+1 запити при великій кількості товарів** (Теоретично): Кожен товар вимагає окремого HTTP-запиту. Якщо сканувати 100+ товарів — 100+ запитів.

2. **Розмір PDF** (Теоретично): При великій кількості товарів PDF може стати великим. Генерація на головному потоці може блокувати UI.

## 15. Архітектура та підтримуваність

### Структурні слабкості

1. **Змішана модульність** (MED-04): `screens/` (layer-based) + `recount/` (feature-based) — немає єдиного принципу організації.

2. **Бізнес-логіка в UI** (HIGH-06): HTTP-запити, парсинг, валідація — у `StatefulWidget`. Відсутній шар сервісів/репозиторіїв.

3. **God classes** (HIGH-06): `_ResultsScreenState` (447 рядків) — усе в одному класі: мережа, бізнес-логіка, UI, навігація.

4. **Відсутність абстракцій** (HIGH-06): Жодного інтерфейсу чи абстрактного класу. `SessionStorage` — конкретний клас без контракту.

5. **Дублювання коду** (HIGH-05): ~129 рядків ідентичного коду.

6. **Відсутність Error Boundary** (IMPR-01): Немає `runZonedGuarded`, немає `ErrorWidget.builder`, немає crash reporting.

### Технічний борг

| Елемент | Вплив |
|---|---|
| Відсутність тестів | Кожна зміна може зламати функціональність |
| Пряма залежність від http | Неможливо замінити HTTP-клієнт |
| Жорстко закодована конфігурація | Неможливо мати dev/staging/prod |
| `recoun`t файли з префіксом | Зайва довжина імен |
| `Provider.of` замість `context.watch` | Потенційні проблеми зі слуханням |

## 20. Підсумковий вердикт

**Продукт НЕ ГОТОВИЙ до використання реальними користувачами.**

### Що абсолютно необхідно виправити в першу чергу

1. **Додати автентифікацію API** — найбільший ризик безпеки
2. **Замінити дебажний підпис на релізний** — другий за критичністю ризик
3. **Захистити локальне сховище даних** — третій критичний ризик
4. **Виправити force-unwrap `_sessionManager`** — ризик падіння застосунку
5. **Виправити fire-and-forget у `dispose()`** — ризик втрати даних

### Найбільший ризик безпеки

**Відсутність автентифікації API** у поєднанні з жорстко закодованим URL. Будь-хто з доступом до APK може витягнути URL та необмежено викликати API, отримуючи доступ до всієї товарної бази з цінами та залишками.

### Найбільший функціональний ризик

**Втрата даних сесій переобліку** через fire-and-forget запис у `dispose()` та незахищений JSON-файл без транзакційності. При збої під час запису всі дані втрачаються без можливості відновлення.

### Найбільша UX-проблема

**Ручне введення штрихкоду обходить валідацію** на екрані сканування, створюючи неконсистентну поведінку: сканування відхиляє коди без префікса 210700, а ручне введення приймає будь-які.

### Найцінніше покращення

**Перенесення бізнес-логіки з UI у сервіси/репозиторії** дасть змогу: (1) додати unit-тести, (2) зменшити дублювання коду, (3) спростити підтримку, (4) полегшити додавання нової функціональності, (5) покращити безпеку через централізоване управління API-запитами.

### Рекомендована наступна дія

Розпочати Етап 0 (негайні виправлення безпеки). Паралельно ініціювати зміни на серверній стороні для додавання автентифікації. Після завершення Етапу 0 — перейти до Етапу 1 з рефакторингом архітектури та додаванням тестів. Очікуваний час до готовності до релізу: **2-4 тижні** при повній зайнятості одного розробника.
